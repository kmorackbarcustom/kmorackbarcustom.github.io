## Defect found by controller review (not by the lane's checks)

`remainingHoldSeconds` returns **`0`** for a genuinely elapsed hold — zero is a real
server value meaning "no time left"; only `null` means "no usable value at all".
The first implementation of WU01 gated the countdown banner on mere non-nullness:

```text
banner guard: holdCountdownText !== null      // "00:00" is not null -> banner renders
```

Consequence: an elapsed hold froze at `00:00` and the rose-coloured expired panel
(`t('step3.expired')` + the "choose a new time" recovery button) became
**unreachable**. The previous behaviour (`timeLeft > 0`) did render it, so this was a
regression that no declared check and no worker self-report caught.

Correction: a single owner of the question, requiring a strictly positive value.

```text
const holdHasTimeRemaining = holdSecondsRemaining !== null && holdSecondsRemaining > 0;
const holdCountdownText = holdHasTimeRemaining ? formatCountdown(holdSecondsRemaining) : null;
```

Controller-run semantics probe over three hold states (mirrors the page's final expressions):

```text

hold expired 60s ago         secs=0     banner=NO          expiredBranch=YES  confirmDisabled=true
expires_at null              secs=null  banner=NO          expiredBranch=YES  confirmDisabled=true
expires_at unparseable       secs=null  banner=NO          expiredBranch=YES  confirmDisabled=true
```
