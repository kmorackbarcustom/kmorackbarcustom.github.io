## 1. Brief section A requirement — resolved from evidence, not assumption

Brief A says *"anon SELECT only on `staff_schedules.shop_id`; anon SELECT only on `shop_holidays.shop_id` …
no table-wide SELECT and no write privilege."*

Read naively, "only on `shop_id`" looks like **reducing** anon to `shop_id`. That reading would have
**broken the live booking page**, which selects:

```text
staff_schedules -> staff_id, day_of_week, is_working_day, work_start, work_end, break_start, break_end
shop_holidays   -> staff_id, holiday_date, reason
```

The proven BK01 R4 runtime repair (the artefact section A says to reconcile *against*) shows the correct
intent, verbatim:

```sql
GRANT SELECT (shop_id) ON local_service.staff_schedules TO anon;
GRANT SELECT (shop_id) ON local_service.shop_holidays TO anon;
```

with post-state verification reading:

```text
anon SELECT on staff_schedules.shop_id = true, shop_holidays.shop_id = true
anon table-level SELECT still FALSE on both; INSERT/UPDATE/DELETE still FALSE on both
Effective anon column set: schedules {shop_id, staff_id, day_of_week, is_working_day, work_start,
work_end, break_start, break_end}; holidays {shop_id, staff_id, holiday_date, reason}
  — "unchanged payload contract plus the single predicate column. No extra column exposure."
```

**Resolution:** section A's deliverable is to **ADD** the `shop_id` predicate grant. The existing column
grants stay. Table-level SELECT and all writes remain FALSE. This is exactly the proven runtime state.
